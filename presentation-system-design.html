~12-minute technical overview

ArbitragePulse

A low-latency price-difference hunter on public blockchains: detect when the same asset trades at different prices on two automated market programs, then execute both legs in one atomic transaction so you either profit or cancel entirely.

Audience: strong software engineering background · no crypto assumed
Focus: architecture · data flow · tradeoffs · capital path · why we built it this way

Slide 1 · ~1 min
Plain-language bridge

Three ideas (no jargon wall)

Shared ledger

Think of a blockchain as a replicated append-only database everyone agrees on. Programs (“smart contracts”) run deterministically when you submit a transaction.

Automated exchanges (DEX)

Instead of a central order book, liquidity lives in pool contracts with formulas (e.g. constant-product). Anyone can swap against them; prices move with each trade.

Atomic arbitrage

Buy cheap on pool A, sell high on pool B inside one transaction. If the round-trip doesn’t meet profit rules, the whole thing reverts—like a database rollback (you still pay network fees).

Our edge is speed + correctness: see price drift early, quote accurately, submit before others, and fail safe on-chain.

Design choice

Most V2 quotes are zero-RPC (event-driven cache). That’s how we hold scan latency under block time on L2s.

Tradeoff

optimistic_submission: true skips Quoter → faster but more on-chain reverts. Production Base config uses Quoter on until the pipeline proves consistent wins.

Slide 5 · ~1 min
Execution & safety

On-chain contract as the safety boundary

What the executor sends

  • One call: executeArbitrage (2-hop) or triangular variant
  • Parameters: tokens, routers, fee tiers, amount, minProfit, deadline
  • Leg 2 sets router amountOutMinimum = amountIn + minProfit

Guards (Solidity)

  • ReentrancyGuard — callback-safe swaps
  • Pausable / Ownable2Step — ops kill switch
  • Router allowlist — only approved DEX programs
  • NotProfitable — final balance check vs minProfit

Off-chain engine softens encoded minProfit (bps slack + multiplier) to reduce “almost profitable” reverts; reverts still possible when pool state moves between detect and inclusion (FCFS ordering).

Slide 6 · ~1 min
Capital model

Small capital today — scaling $1k → $100k

Problems at ~$1k capital today

  • Size ceiling — YAML trade_amount: "1000" USDC; contract balance caps each arb
  • Price impact — $1k already moves thin 0.01% pools; edge shrinks vs $10k+ competitors
  • Fixed recovery bar — sell leg must return ≥ amountIn + minProfit; small misses → revert (see Slide 12)
  • Gas overhead — Base L1 data fee + ~350k gas on failure dilutes micro-profits
  • Underfunded pairs skipped — engine balance guard refuses routes the contract cannot fund

Scale plan (owned inventory)

  • Phase 1 (~$1k) — prove confirmed wins with Quoter on; tune detection vs reverts
  • Phase 2 ($5k–20k) — reinvest profit into contract inventory
  • Phase 3 ($50k–100k) — raise trade_amount, more pairs in parallel
  • Phase 4 — enable optimize_size where latency budget allows

Latency vs correctness (the main tension)

Slide 9 · ~1 min
Concurrency

Engine runtime model

flowchart TB
  subgraph per_chain [Per enabled chain task]
    WS[WS provider blocks + logs]
    Poll[Timer scan_interval_ms]
    Pend[Optional mempool monitor]
    Strat[Strategy + PoolCache]
    ExecM[Executor Mutex]
  end
  WS --> Strat
  Poll --> Strat
  Pend --> Strat
  Strat -->|best opp| Scan[scan.rs candidate loop]
  Scan -->|prepare lock brief| ExecM
  ExecM -->|release lock| Send[send_raw / send_tx]
  Send -->|spawn| Receipt[receipt waiter]

Split-lock pattern: hold mutex only for nonce + tx build; sign and broadcast outside lock so block events aren’t starved. Cooldowns per route fingerprint prevent hammering the same failing path.

Slide 10 · ~50s
Observability

How we know what happened

Structured logs

  • exec_send — pipeline_ms, tip, pair, tx hash prefix
  • exec_confirm — ok, block, tx_index, gas_used
  • Heartbeat — opps, bestV, quotes (Quoter path)

Dashboard + API

  • WebSocket log stream (opportunities, trades, errors)
  • REST /stats with API key auth
  • Prometheus counters (attempts, failures, profit)
  • SQLite trade history for post-mortems

A “success” in the UI means receipt.status = 1—not merely “tx submitted”.

Slide 11 · ~50s
Failure modes

What we learned in production (Base)

Symptom

  • Explorer shows “Fail”, no revert string
  • Many submits, zero confirmed profits

Root cause (example)

  • Sell leg returned ~999.44 USDC vs on-chain min ~1000.02 USDC
  • Phase-1 quote optimistic vs thin 0.01% fee pool
  • Fix path: Quoter on + tighter detection buffers

Prevention (Lab)

  • All edge cases reproduced in the local lab / CLI against an Anvil mainnet fork before deploying engine updates
  • Rust scenarios + mock routers for regression; production calldata replayed with cast run
  • Optional preflight_eth_call + RPC revert hex parsing in engine

Post-mortem on-chain: fork trace when a mined tx still surprises us—never the first time we see a path.

Close

Summary

  • ✓ Problem: exploit transient price gaps across automated pools—safely and fast.
  • ✓ Shape: Rust detector + Solidity executor + React ops plane + YAML config.
  • ✓ Core tradeoff: milliseconds vs quote fidelity on competitive L2 sequencers.
  • ✓ Trust boundary: smart contract atomicity; engine is optimization layer only.
  • ✓ Capital path: ~$1k inventory today; scale to $100k by reinvesting confirmed wins into the contract.
  • ✓ The startup transfer: the core engineering challenge here—managing asynchronous, event-driven concurrency and handling messy data under strict time constraints—maps directly to building scalable backend ingestion engines (e.g. Fastalyze logistics document pipelines).
