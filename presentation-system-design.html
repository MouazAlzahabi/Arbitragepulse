The problem

Same coin, two prices — for seconds

What happens

USDC might cost $0.9998 on Exchange A and $1.0004 on Exchange B. That tiny gap is profit — if you act before someone else closes it.

Gaps appear after big trades, new listings, or slow price updates. They are small and short-lived.

What we need

  • Monitor many token pairs 24/7
  • Spot a gap worth more than fees
  • Execute both legs together — profit or nothing

Say: “We’re not predicting the market — we’re catching pricing mistakes between venues.”

Crypto primer

Five concepts to get onboard

Blockchain

A public ledger everyone copies. You submit a transaction; if accepted, the change is permanent.

Smart contract

Code on the ledger — like a small program that runs when you call it. Our contract runs the two swaps for us.

DEX (decentralized exchange)

No human broker. Liquidity sits in pools; a formula sets the price. Anyone can swap against them.

Token pair

Two assets in one pool — e.g. USDC/WETH. We compare the same pair across different pools or exchanges.

Atomic transaction

Buy and sell in one transaction. If the round-trip isn’t profitable, everything rolls back — except the network fee you already paid.

Gas & priority fee

You pay the network to include your transaction. A higher tip can get you earlier in the block when competition is tight.

Why this is hard

Challenges before profit

Market & competition

  • Many bots hunt the same gaps — first in the block often wins
  • Priority fees — pay more to jump the queue, but that eats margin
  • Stale prices — by the time you trade, the gap may be gone

What to monitor

  • Pair selection — thousands of pools; most never gap
  • Thin liquidity — big trades move the price against you
  • False positives — math says profit, chain says revert

Engineering

  • Latency — every extra 100 ms can mean a lost trade
  • Correct quotes — fast estimates vs slow accurate checks
  • Capital — need inventory in the contract to trade size

Operations

  • Failed txs still cost gas on many chains
  • Config tuning — thresholds, routers, pairs change often
  • Visibility — “submitted” ≠ “profitable”

Data flow

From price update to confirmed trade

Six steps on the happy path — think of it as a pipeline, not one big loop.

1
Listen

New blocks and swap events update our in-memory price cache. (<1 ms)

“We react to chain events, not slow polling alone.”

2
Detect

Compare prices across configured pairs. If spread > fees + buffer → candidate trade. (1–2 ms)

3
Prepare

Build the transaction: which pools, how much, minimum profit, gas tip. (~10 ms)

4
Submit

Broadcast to several RPC endpoints at once — race to reach the sequencer first.

5
Confirm

Wait for receipt. Success = status 1 on-chain. Log to DB and push to dashboard.

6
Learn

Metrics and logs feed the next tuning cycle — which pairs, which settings work.

Finding opportunities

How we decide “is this worth sending?”

  F --> G{Spread big enough?}
  G -->|no| X[Skip]
  G -->|yes| H[Double-check with on-chain quote]
  H --> I{Still profitable?}
  I -->|no| X
  I -->|yes| J[Send to executor]

Fast path (always on)

We keep pool state in RAM from WebSocket events. Most math runs locally — no extra network round-trip.

“Speed comes from not asking the chain on every scan.”

Safety check (Base: on)

Before sending, we ask the chain “what would this swap actually return?” Skipping this is faster but causes more failed transactions.

Execution & safety

One transaction, two swaps, strict rules

flowchart LR
  Start[Start with USDC] --> Buy[Buy on cheap pool]
  Buy --> Sell[Sell on expensive pool]
  Sell --> Check{Got back ≥ start + profit?}
  Check -->|yes| Done[Keep profit]
  Check -->|no| Rev[Revert all]

Contract enforces

Only approved routers. Pause button for ops. Reentrancy protection.

Engine optimizes

Picks pairs, sizes, gas tip, timing. Can be wrong — contract is the final judge.

Reality check

Prices move between detect and inclusion. A “good” opportunity can still fail on-chain.

Staying responsive

How the engine handles many events at once

One long-running task per chain. Think: a newsroom that never stops listening.

Always listening

  • WebSocket — new blocks and pool updates stream in
  • Timer — backup scan every few seconds
  • Price cache — RAM, updated on every event

When we find a gap

  • Pick the best candidate for this block
  • Build tx quickly — don’t block the listener
  • Send in parallel; confirm in the background
  • Cooldown on routes that keep failing

Quality before mainnet

Test like prod, ship with confidence

Local lab

Fork mainnet with Anvil. Run the same Rust engine against fake and real router bytecode — no gas cost.

Replay failures

When a tx fails on Base, we trace it locally. Was the quote wrong? Pool too thin? Fix config before the next deploy.

Dry-run mode

Engine starts with DRY_RUN=true — full detection and tx build on real RPCs, no mainnet submits. Validate pair tuning without gas. Flip live only when metrics look right.

Gradual rollout

After dry-run looks good, go live with stricter checks first — on-chain quote double-check, then optional preflight simulation — when accuracy matters more than raw speed.

Engineering lesson: latency and correctness are a dial, not a one-time choice. We tune per chain as we learn what wins.

Observability

How we know if we actually made money

1
Live dashboard

WebSocket stream: opportunities spotted, txs sent, errors. Shows dry-run vs live so ops know if we’re shadowing or broadcasting.

2
Structured logs

exec_send = we broadcast (or log “would send” in dry-run). exec_confirm = chain answered. Each line has pair, timing, gas.

3
Success definition

Submitted ≠ won. We only count profit when the receipt says success (status = 1).

4
History & metrics

SQLite for post-mortems; Prometheus counters for attempts, failures, and P&L — all tagged dry_run=true/false so shadow runs don’t mix with live.

Takeaways

Three things to remember

Problem

Tiny price gaps between automated exchanges — monitor fast, act atomically.

Shape

Rust finds gaps; Solidity enforces profit; dashboard proves what landed on-chain.

Edge

Milliseconds + honest quotes + ops discipline — same skills required for high-throughput data ingestion and processing pipelines.
